# Agent Note: 将 Docker 发行版升级至 Session V3

Status: implemented

[English](2026-09-13-docker-session-v3-upgrade.md) | 中文

## 问题

Docker 发行版在 `0.1.2-alpha.1` 上扩展了 OceanBase 存储、Redis 缓存、可信用户归属、临时附件、Nacos 配置及跨副本 Web 确认。上游 `dsh-v0.1.5-rc.2` 将 Session 存储改为句柄和 V3 记录，修改了临时流与投影，并增加通用文件上传。文本合并不能证明这些本地行为得到保留，或归档数据保持不变。

## 决策

Docker 发行版集成上游 `dsh-v0.1.5-rc.2`，对应提交 `fb2c4b9e698e30edb738bca4cf0618587db7d203`，并在整个运行时采用其 API。通过测试的升级前检查点保留在 `codex/upgrade-0.1.5-baseline`；部署与源码集成是独立操作。

MySQL 提供方实现基于句柄的持久化，包含有序追加、失败批次保留、刷新和关闭时排空、读取新鲜度及独占写入归属。数据库写入隔离及跨副本取消继续作为权威机制，不依赖 Redis 淘汰策略。共享的累计 Assistant 快照在持久完成记录提交前保留跨副本的 Web 实时进度。

上传凭证使用现有 KV 行，并绑定用户、Session 及物理数据库行。缺失或无权访问的 Session 在读取字节前以 `session/not-found` 拒绝操作，数据库故障仍作为错误报告。凭证消费写入 Session 日志，防止进程替换后重用。二进制附件保留在共享临时文件中。当前 JSONL 保留用户归属，Host 消费方共享同一个用户上下文 peer 实例。

运维方选择将历史对话保留归档，不转换或继续执行它们。表、字段及索引保持不变。新副本统一使用一个未使用的 Nacos `deployment.appName`，旧 Session 和 KV 行保留在原应用标识下。这也会选择空的工作区及应用 KV 状态，但 Nacos 设置和凭据可继续使用。启动流程不会更改应用标识、重写旧行或导入历史 Docker 事件。数据库备份及旧版本作为回退来源，已提交的历史 JSONL 世代及上游读取器保持不变。

[用户归属](2026-09-06-oceanbase-user-ownership.zh.md)、[Redis 与临时附件](2026-09-12-redis-session-context-and-temporary-attachments.zh.md)、[持久化确认](2026-09-13-durable-web-confirmation.zh.md)及 [Docker CI](../process/2026-09-13-docker-ci-scope.zh.md) 决策继续有效。其中关于安全、保留、执行和 CI 选择的理由仍约束本发行版。

## 曾考虑的替代方案

**只复制选定的上游功能。** Session、投影、上传和网关修改涉及共享接口；单独复制会保留混合版本运行时，并增加未来的重复集成工作。

**使用发布版本目录替换整个 fork。** 这会丢弃部署配置、数据库存储、租户数据保护和共享确认，而不是升级它们。

**在启动时重写正在使用的数据库。** 这会让失败的部署修改回退数据源，并让每个副本都可能执行本应由运维控制的数据转换。

**将历史 Docker 对话转换为 V3。** 继续执行旧对话不在请求范围内。保留原始行避免了专用的历史问题及附件转换，代价是新应用无法展示或继续执行旧对话。

## 影响

归档保留数据库数据，不提供当前浏览器读取器，也不保留已过期的临时文件。更换应用标识也会选择空的工作区及应用 KV 状态。旧副本必须停止，保留的行才能成为稳定归档；复用旧应用标识会选中不兼容记录。文件共享与租约归属仍是独立问题。升级后的数据没有降级读取器，回退使用保留的原应用标识，不能包含新增 V3 写入。

源码集成不会部署版本、更改 Nacos 条目或归档运行中应用的数据。隔离测试使用受控模型，外部提供方行为和原生平台矩阵仍是独立检查。Docker 集成套件需要足够内存来运行额外的 OceanBase 实例，并在仅删除自身容器和卷之前保留诊断文件。
