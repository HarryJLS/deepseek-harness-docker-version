DSH 容器部署手册

一份基础镜像服务多个应用。本手册讲具体怎么配：起栈、五个 Nacos 条目怎么写、多应用怎么隔离、插件怎么上架、出错怎么查。全文的组织依据只有一条 —— 改一个值要付出什么代价：改完就生效、改完要重启、还是要重建镜像。

1五分钟起一套栈

本地起一套完整环境：harness 本体、Nacos、OceanBase（MySQL 模式）。

docker compose -f deploy/docker-compose.yml up -d --build
服务地址用途
dshhttp://localhost:3080harness 本体
Nacos 控制台http://localhost:8080改实时配置
OceanBaselocalhost:2881会话与存储

此时还不能对话 —— 没有 API key。最小可用配置只需一件事：在 Nacos 控制台新建配置，Data ID dsh-credentials.yaml，Group DEFAULT_GROUP，类型选 yaml：

refs:
  DEEPSEEK_API_KEY: sk-你的真实key
records: {}

发布后 10 秒内生效，无需重启。打开 http://localhost:3080 即可使用。

也可以用容器环境变量 DEEPSEEK_API_KEY 注入。环境变量优先且只读 —— 设了它，Nacos 里的同名 ref 会被遮蔽，而且从界面写入会被显式拒绝，不会出现「提示保存成功但解析仍返回旧值」。

2配置放在哪

只有一个判断标准：这个值在连上 Nacos 之前需不需要先读到？

需要 → 只能是静态的。否则会形成循环依赖：要读配置得先连 Nacos，而 Nacos 的地址本身就在配置里。

类别包含改法生效
静态 监听地址端口、Nacos 与数据库坐标、能力接缝挂哪个实现 改 packages/bundle/docker/cordis.patch.yml → 重建镜像 下次部署
实时 模型路由、API key、agent 参数、权限、全局提示词、插件的挂载与配置 Nacos 控制台改内容 秒级
需重启 应用名、插件清单 Nacos 控制台改内容 重启容器

第三类是本手册里最容易踩的一类。它们同样写在 Nacos，但改完必须重启 —— 原因见 第 7 节，不是条目的限制，是模块解析时机决定的。

3环境变量

写在 docker-compose.yml 的 dsh.environment 下，或 K8s Deployment 的 env。这里只放「连上 Nacos 之前必须知道」的东西。

Nacos 与数据库坐标

变量默认说明
DSH_NACOS_HOST / _PORTnacos / 8848地址；gRPC 端口由 HTTP 端口 +1000 推导。单节点 standalone 即可，不需要集群
DSH_NACOS_NAMESPACE空（public）命名空间 id。各应用用自己的命名空间隔离
DSH_NACOS_GROUPDEFAULT_GROUP配置分组
DSH_NACOS_USERNAME / _PASSWORD未设Nacos 开鉴权时使用
DSH_MYSQL_URL未设完整连接串；设了就忽略下面的分散字段
DSH_MYSQL_HOST / _PORToceanbase / 2881OceanBase 地址
DSH_MYSQL_DB / _USER / _PASSWORDdsh / root / 未设数据库名与凭据；也可在 Nacos 的 deployment.database 中声明

可选覆盖

变量默认说明
DSH_PORT3080容器内监听端口
DSH_APP_NAMEdsh应用名的兜底值；settings 条目里的 deployment.appName 优先

部署侧只需要知道去哪里连。「我是谁」写在应用自己的 Nacos 配置里（deployment.appName），不必在每份部署描述里重复。

4五个 Nacos 条目

五个条目在每个部署里名字完全相同 —— 每个应用拥有自己的 Nacos 命名空间，隔离由命名空间完成，不靠给条目起不同的名字。这样基于同一镜像的应用不需要做任何命名决策。

Data ID类型管什么生效
dsh-settings.yamlyaml应用身份 + 用户设置秒级
dsh-credentials.yamlyamlAPI key 与授权记录秒级
dsh-plugins.ymlyaml插件挂载 / 禁用 / 改配置秒级
dsh-plugin-roster.ymlyaml装哪些插件、从哪个仓库装需重启
dsh-agents.mdtext全局提示词新会话

新建配置时记得选对类型：YAML 条目选 yaml，控制台才有语法高亮和校验。通过 API 发布时不传 type 会默认成 text。功能上不影响解析，但控制台体验会变差。

dsh-settings.yaml秒级生效应用身份 + 用户设置

键是命名空间名，值是该命名空间的用户覆盖层。只写要覆盖的，没写的落回 schema 默认值。

顶部的 deployment 不是设置命名空间，是这个部署的身份声明 —— entrypoint 在 harness 启动前读它，决定写入各张表 app 列的值以及数据库连接凭据。

# 应用身份。改了要重启容器：表打开后无法搬家。
deployment:
  appName: order-svc

# 新会话默认用哪个模型
agent-default-model:
  provider: deepseek-official
  model: deepseek-v4-flash
  reasoningEffort: high

# DeepSeek 官方适配器：这个应用允许用的模型清单
llm-deepseek:
  models:
    - id: deepseek-v4-flash
      name: DeepSeek-V4-Flash
      description: 快速、经济，适合聚焦、常规或并行任务。
      contextWindow: 1000000
      inputModalities:
        - text

# agent 主循环：单步内最多并发多少个工具调用。1 = 串行。
agent-loop:
  maxParallelToolCalls: 4

# 子 agent 模型选择。false = 跟随主 agent 的模型。
subagent-model-selection:
  enabled: false
  allowedModels: []

接入第三方模型供应商

用 llm-pi-ai，填了 provider 才会注册路由：

llm-pi-ai:
  providers:
    my-vendor:
      displayName: 内部网关
      apiKeyEnv: MY_VENDOR_API_KEY    # 对应 credentials 条目 refs 里的键名
      api: anthropic-messages          # 取值：anthropic-messages | openai-responses
      baseURL: https://llm.internal.example.com
      models:
        - id: internal-large
          name: 内部大模型

实例注册的命名空间不止这些（还有 permission、shell、locale、ui-theme、web-search-deepseek 等）。各命名空间接受哪些字段以界面的设置页为准 —— 在设置页改一次，再回 Nacos 看条目变成什么样，是确认字段名最可靠的方式。乱填的键会被 schema 拒绝。

界面写入是按命名空间读改写（{ ...current, [ns]: section }），所以 deployment 这个非命名空间的键不会被冲掉。

dsh-credentials.yaml秒级生效API key 与授权记录
# refs — 按环境变量名索引的密钥，供 LLM 适配器按名解析
refs:
  DEEPSEEK_API_KEY: sk-你的真实key
  MY_VENDOR_API_KEY: sk-第三方供应商的key

# records — 授权凭据记录，没有上层可遮蔽，存在即事实
records: {}

三条规则：

  • 容器环境变量优先且只读。设了 DEEPSEEK_API_KEY 环境变量，这里的同名 ref 被遮蔽。
  • 写入被遮蔽的引用会显式拒绝，不会静默忽略。
  • records 没有上层，存在即生效。

这个条目是明文，Nacos 不额外加密。请放在读权限受限的独立命名空间，并给 Nacos 开启鉴权。

dsh-plugins.yml秒级生效插件补丁层

会被写到 profile 的 cordis.patch.yml，Loader 监听该文件，所以改完无需重启。内容是 Loader 的 patch 数组，三种写法：

# 1) 改已装插件的配置
#    注意：整块 config 会被替换，要写全这一行拥有的所有键
- id: session-title
  config:
    fallbackMaxWords: 5
    fallbackMaxBytes: 40
    maxTitleBytes: 120

# 2) 临时禁用一个插件
- id: demo-plugin
  disabled: true

# 3) 挂载一个已安装、但自身没声明 dsh.bundle 的包
- insert:
    - id: my-plugin
      name: my-plugin-package
      config:
        someOption: true

不做任何覆盖时写空数组：[]

不要 insert 一个已经自带 dsh.bundle 的包 —— 它会被挂载两次。持有具名资源的插件第二次会报 already-open，容器起不来。

dsh-plugin-roster.yml需重启插件清单
# 私有仓库地址。不写则用 DSH_NPM_REGISTRY，再不写用 pnpm 默认源。
registry: https://npm.internal.example.com/

# 私有仓库 bearer token。仓库匿名可读时删掉这行。
token: npm_xxxxxxxxxxxxxxxx

packages:
  - dsh-plugin-example@1.2.0
  - '@acme/dsh-internal-tools'

公共源、无鉴权时的最简形式：

packages:
  - dsh-plugin-example@1.2.0

清单是声明式的：删掉一行，下次启动会卸载那个包。只卸载由清单装过的（记录在 profile 的 dsh.roster），运维手工 dsh plugin add 的不动。

配了 token 却没配 registry 会直接报错拒绝启动 —— 因为这意味着运维以为有鉴权而实际不会发生，私有包会以一个没有原因的 404 失败。

dsh-agents.md新会话生效全局提示词

纯 Markdown，被写到 $DSH_HOME/AGENTS.md，作为用户级全局指令注入每个会话的提示词。

5多应用共用基础设施

一份基础镜像，多个应用。Nacos 各自隔离，OceanBase（MySQL 模式）共用一个数据库。

数据库和表是共用的，应用通过每张表第一列的 app 值隔离。应用在自己的 dsh-settings.yaml 里声明名字：

deployment:
  appName: order-svc

部署描述里只写坐标，不写身份：

services:
  order-svc:
    image: your-registry/dsh-base:0.1.2
    environment:
      DSH_NACOS_HOST: nacos.internal
      DSH_NACOS_NAMESPACE: order-svc        # 这个应用自己的 Nacos 命名空间
      DSH_MYSQL_HOST: oceanbase.internal
      DSH_MYSQL_PORT: '2881'
      DSH_MYSQL_DB: dsh
    ports: ['3080:3080']

  billing-svc:
    image: your-registry/dsh-base:0.1.2     # 同一份镜像
    environment:
      DSH_NACOS_HOST: nacos.internal
      DSH_NACOS_NAMESPACE: billing-svc      # 只有这里不同
      DSH_MYSQL_HOST: oceanbase.internal
      DSH_MYSQL_PORT: '2881'
      DSH_MYSQL_DB: dsh
    ports: ['3081:3080']

应用名如何隔离数据

deployment.appName写入的 app 值
未声明dsh
order-svcorder-svc
Order ServiceOrder Service
2fa2fa

应用名原样存储，不做小写化、下划线折叠或其他转换。应用查询数据时应带上 WHERE app = '...' 条件。

不要绕过 app 条件查询或修改数据。六张表的主键都包含应用维度；应用改名后会访问新的数据分区，旧值仍保留在原来的 app 值下，不会自动迁移。

启动顺序

读环境变量 → 连上应用自己的 Nacos 命名空间 ↓ 读 dsh-settings.yaml → 取 deployment.appName = order-svc ↓ 写入 /run/dsh-resolved.env → entrypoint source 进环境 ↓ 读 dsh-plugin-roster.yml → 从 npm 仓库装插件 ↓ harness 启动 → 连接 OceanBase → 使用 app = order-svc → 建表或检查表 → 服务就绪
  • 数据库角色通常只需要表级 DML 权限；缺表时才需要 DDL 权限，或由 DBA 先执行预建表脚本。
  • 改名不会迁移数据：容器会使用新的 app 值，旧值的行原样保留。

6数据库预建表

生产环境通常不给应用 DDL 权限 —— 表由 DBA 建好，应用角色只有增删改查。本节是完整建表脚本。

IF NOT EXISTS 不豁免权限检查。应用启动时会先查 information_schema：六张表齐全就完全跳过 DDL，缺任何一张才尝试创建。生产环境可由 DBA 预先执行脚本，让应用角色只保留 DML 权限。

情况结果
表已建好，角色无 DDL 权限正常启动 跳过全部 DDL
表未建，角色有 DDL 权限正常启动 自动建表
表未建，角色无 DDL 权限拒绝启动 明确报 permission denied

最后一种会明确失败：带着不存在的表提供服务，会在第一次写入时才报错，那时已经有用户在用了。

建表脚本

仓库里的完整脚本是 deploy/schema-mysql.sql，适用于 OceanBase 的 MySQL 模式。脚本创建 dsh 数据库和六张带 dsh_ 前缀的表；所有应用共用这些表，通过 app 列隔离。

obclient -h127.0.0.1 -P2881 -uroot@test -pdsh
source deploy/schema-mysql.sql;

-- 只查看某个应用的数据
SELECT session_id, seq
FROM dsh_session_event
WHERE app = 'order-svc'
ORDER BY session_id, seq;

六张表存什么

表存什么
dsh_session会话头。revision 每次写入递增，用于判断某副本持有的视图是否过期
dsh_session_event会话事件日志，一行一事件，按 seq 有序。可按 seq 寻址，投影从水位线恢复时只读后缀
dsh_kv_unit各存储单元的格式版本戳。版本不匹配会拒绝打开而非静默迁移
dsh_kv_record存储记录。当前使用者：会话投影缓存、工作区、消息反馈
dsh_kv_global各单元的全局单例槽
dsh_attachment_object归一化后的图片二进制，按内容寻址。去重靠主键冲突，无需额外逻辑

模型请求用的派生图片变体不落库，留在容器本地临时目录。每个变体都是「引用 + 路由策略」的确定性函数，被替换的容器会重新生成完全相同的字节。判断原则：只有无法重算的东西才需要持久化。

7插件：从写到上架

三种来源，各有各的位置和适用场景。

来源放在哪适用
仓库内置/app/packages/<组>/<包>/（镜像里）首版默认插件集，随镜像发布
Nacos 清单/var/lib/dsh/profiles/web/node_modules/各应用的个性化插件
DSH_PLUGINS同上与清单等价，用环境变量固定时

写一个插件

// index.js
import { z } from 'zod'

export const name = 'dsh-demo-plugin'

// 注入 storageDomain 而不是 storage：
// 前者是域层挂好后才提供的服务，注入 storage 会在任何 form 挂上之前就激活。
export const inject = ['storageDomain']

const DOMAIN = {
  name: 'demo_plugin',              // 必须匹配 ^[a-z][a-z0-9_]*$
  version: 1,
  tables: {
    loads: { valueSchema: z.object({ at: z.string(), app: z.string() }) },
  },
}

export async function apply(ctx) {
  const domain = await ctx.storageDomain.open(DOMAIN)
  ctx.effect(() => async () => { await domain.close() }, 'demo domain')

  const at = new Date().toISOString()
  await domain.table('loads').put(at, { at, app: process.env.DSH_APP_NAME ?? 'dsh' })
}

package.json 里声明 dsh.bundle 就会自动挂载，不需要在 dsh-plugins.yml 里再写一行：

{
  "name": "dsh-demo-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dependencies": { "zod": "^4.4.3" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
# cordis.patch.yml —— 这个包自己的挂载层
- insert:
    - id: demo-plugin
      name: dsh-demo-plugin

没声明 dsh.bundle 的包只会作为普通依赖装上，必须在 dsh-plugins.yml 里写 insert 才会挂载。

发布并上架

# 1. 发到私有仓库
npm publish --registry https://npm.internal.example.com/

# 2. 在 Nacos 的 dsh-plugin-roster.yml 加一行
#    packages:
#      - dsh-demo-plugin@0.1.0

# 3. 重启容器
docker restart <容器名>

启动日志会显示：

entrypoint: deployment.appName = order-svc (from the settings entry)
entrypoint: dsh-plugin-roster.yml declares 1 plugin package(s)
entrypoint: installing 1 plugin package(s) from https://npm.internal.example.com/
+ dsh-demo-plugin 0.1.0

为什么装插件必须重启

Loader 在组合插件树时一次性解析 profile 的模块。往运行中的进程里装一个包，Loader 看不见它 —— 无论用什么方式请求挂载都不行。所以安装动作放在 entrypoint、harness 启动之前。

Nacos 换来的是集中编辑（不用重新部署、不用改环境变量、每应用一个条目），不是免重启安装。

动作是否需要重启
装一个新包 / 卸载一个包需要
挂载已装的包不需要
禁用 / 重新启用已挂载的插件不需要
改已挂载插件的 config不需要

8排错

容器起不来

docker logs <容器名> 2>&1 | tail -40
日志原因处理
domain 'xxx' is already open插件被挂载两次从 dsh-plugins.yml 删掉 insert，包自带 dsh.bundle 就够了
ERR_PNPM_FETCH_401私有仓库鉴权失败检查清单条目的 token 是否为空
a plugin-registry token needs a registry配了 token 没配 registry补上 registry
must match /^[a-z][a-z0-9_]*$/应用名不合法换成字母开头的名字
ERR_MODULE_NOT_FOUND插件依赖没装上确认依赖写在插件 package.json 的 dependencies

构建失败但显示成功

docker compose build 有时构建失败却返回 exit 0。先判断镜像是否真的更新了：

docker images dsh-dsh --format '{{.CreatedSince}}'

显示的时间不是刚才，说明没更新。看真实原因：

docker compose -f deploy/docker-compose.yml build --progress=plain dsh 2>&1 | grep -E 'ERROR|ERR_'

最常见的是 ERR_PNPM_OUTDATED_LOCKFILE —— 改了任何 package.json 后要跑 pnpm install 并把 pnpm-lock.yaml 一起提交。

Nacos 改了不生效

先确认改对了命名空间 —— 各应用的配置在各自的命名空间里，条目名是相同的，很容易改错地方。

docker exec <nacos容器> sh -c 'curl -s \
  "http://127.0.0.1:8848/nacos/v3/admin/cs/config?dataId=dsh-settings.yaml&groupName=DEFAULT_GROUP&namespaceId=order-svc" \
  -H "serverIdentity: security"'

然后按类型判断：插件清单和应用名本来就需要重启；其余条目应在 10 秒内生效。

确认数据属于哪个应用

docker exec <oceanbase容器> obclient -h127.0.0.1 -P2881 \
  -uroot@test -pdsh -Ddsh -e \
  "select app, count(*) from dsh_kv_record group by app;"

docker exec <oceanbase容器> obclient -h127.0.0.1 -P2881 \
  -uroot@test -pdsh -Ddsh -e \
  "select unit, count(*) from dsh_kv_record where app = 'order-svc' group by unit;"
